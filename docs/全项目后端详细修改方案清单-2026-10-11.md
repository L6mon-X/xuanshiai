## 二、口径与优先级

### 2.1 优先级定义

| 级别 | 判定标准 | 处理时限 |
| --- | --- | --- |
| **P0** | 安全边界漏洞、功能实际不可用、资金 / 隐私不可控 | 立即，本批次内必须关闭 |
| **P1** | 产品闭环关键环节缺失，影响业务可运营性 | 本迭代内 |
| **P2** | 运营完善、体验优化、文档一致性 | 排期靠后 |

### 2.2 工时口径

- 单位：**人日**（1 人日 = 8 小时），含编码 + 自测 + 文档同步，不含 Code Review 等待与真实环境演练。
- 估算基准为熟悉本项目的 1 名后端工程师；多人并行按依赖折算。
- 标注 `+外部` 的条目含等待外部环境 / 凭据 / 审批的时间，不计入纯编码工时。

### 2.3 完成定义

一条任务标记完成，必须同时满足：

1. 代码已提交，且**路由可被真实调用**（仅存在服务函数不算）；
2. 有自动化测试（单元或集成），或说明为何无法自动化；
3. 相关 `docs/api/*.md` 已同步；
4. 属权限 / 数据范围类的，附**真实多组织账号**越权验证记录（可延后到批次 E 统一做，但须留 TODO 标记）。

## 三、跨模块缺陷修复清单（D-13 ~ D-22）

### D-13 C 端账号注销入口缺失 + 注销闭环不完整【严重度：高】

**现状**：全仓无任何 `INSERT INTO user_cancellation`，C 端无注销申请入口，仅后台 `routes/user_cancellation_admin.py` 只读 / 审批（建表 `app/db/business_schema.py:1449`）。审批即 `status=3`，不清手机号 / 昵称，不失效会话，无冷静期（`services/user_cancellation_admin.py:140-152`）。

**修改方案**
1. 新增 C 端端点 `POST /auth/cancellation`（或 `/users/cancellation`）写 `user_cancellation`（状态=待审），带二次确认与在途业务校验（未结订单 / 未结约见 / 余额拦截或提示）。
2. 冷静期：待审 → 冷静期（N 天，可配置）→ 生效；冷静期内可撤回。
3. 生效动作：数据匿名化（清手机号 / 昵称 / 头像 / 设备信息，保留必要留存字段并做不可逆散列）、强制失效全部 `user_session`、级联下架动态 / 关闭进行中的关系与约见。
4. 新增定时任务（复用 worker 框架），补审计。

**验收标准**：C 端可提交并撤回注销；冷静期结束自动生效；生效后该用户全部登录态失效、手机号 / 昵称不可查、历史内容按规则处理；全流程有审计。

### D-14 实名两套并行审核写不同列 → 门禁不可达【严重度：高】

**现状**：旧后台审核写 `realname_status`（`services/auth.py:364`）；会员认证后台审核写 `face_verified`（`services/member_auth_admin.py:543`）；而 C 端门禁读 `realname_status==2`（`dependencies.py:109`）→ **在「会员认证后台」通过实名不会让用户过门禁**；人脸门禁（`dependencies.py:114-125`）已用于社区发帖（`routes/community.py:210,261`），但人脸完全无适配层 / 无入口（`docs/api/认证.md:247-256`），导致「实名 → 人脸 → 发帖」主闭环生产不可达。

**修改方案**
1. 统一实名写入列（建议全部写 `realname_status`，`face_verified` 作为人脸专属标记保留但门禁以 `realname_status` 为准）；两个后台入口收敛到同一服务函数。
2. 历史数据回填：`face_verified=1` 且 `realname_status!=2` 的记录按规则补齐。
3. 人脸适配层：定义 provider 接口 + mock 实现 + 真实供应商占位（真实接入归门禁，见第七节）；门禁在人脸未接入时明确 fail-open 或 fail-closed 并在文档标注。
4. 补测试：两后台入口审核通过后，C 端门禁均可放行。

**验收标准**：无论从哪个后台入口审核通过，C 端门禁读取的实名状态一致；人脸未接入时社区发帖门禁行为在配置与文档中明确。

**现状**：`WECHAT_PAYMENT_MODE=real` 时回调固定 503（`services/membership.py:246-248`）；且 `signature` 参数收下即弃，不验签、不校验金额（`:246-263`）。

**修改方案**
1. 作为 MP-C-01（真实支付接入）的**前置**：先补齐回调框架——验签、金额一致性校验、订单归属校验、幂等、异常落库。
2. 在 `mock` 模式下也用同一回调编排（仅验签实现可替换），保证链路一致。
3. 补测试：伪造签名 / 金额不符 / 重复回调均被拒且留审计。

**验收标准**：回调必须验签通过且金额与订单一致才履约；非法回调返回明确错误码并留审计。

## 六、验收标准（按类别）

### 6.1 功能类

- 每条新增 / 修复路由均能在 OpenAPI 中看到，且文档描述与实际行为一致。
- 所有「涉及金额」的动作（支付、开通、续费、退款、提现、奖励、积分兑换）满足：幂等键可控、重复请求不重复扣款 / 发放、失败有明确状态与审计、**必须验签且金额与订单一致**。

### 6.2 安全类

- 权限：不存在任何走后台鉴权却不做权限校验的路由（`test_admin_permission_coverage.py` 持续保证）；所有引用到的权限码必须已登记种子（D-17 新增静态测试）。
- 数据范围：`ALL / SELF / STORE / ORGANIZATION` 四档全覆盖，**无绑定组织时返回 0 条**（fail-closed）；不再出现 `1=1` 无过滤查询。
- 账号：注销后全部会话失效、敏感字段不可查；被封禁用户无法通过刷新续命。
- 越权：附真实多组织账号验证记录（A 组织访问 B 组织 → 0 条或 404）。

### 6.3 可靠性类

- 实时通道（直播 WS、聊天 WS、语音）：Redis 不可用时 fail-closed 且给出明确关闭码；断线重连可补发；跨进程单会话互斥生效。
- 异步投递（通知、直播事件、Outbox、积分事件）：有重试、有死信、有崩溃恢复。
- 配置：后台修改的配置项**必须在运行时真实生效**（消费回归测试保证）。

### 6.4 文档类

- `docs/api/*.md` 中路径与 OpenAPI 逐条对齐；`待完成事项.md` / `后台缺失功能清单` / `m7-merchant.md` / `m7-activity.md` / `AI军师.md` / `后端接口对接缺口清单.md` 的过期结论全部修正（跨模块问题 P5）。
