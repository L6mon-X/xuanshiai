# 换绑手机号（2026-11-02）

> 本文补充 `docs/api/认证.md` 中「绑定手机号」相关契约。文字与 `认证.md` 冲突时以本文为准。

## 背景与安全变更（必读）

修复前 `POST /api/v1/auth/bind-phone` 的实现是：校验**新手机号**的验证码 → 直接
`UPDATE users SET phone = ...`。它不校验旧号、不判断当前是否已绑定、不走敏感操作幂等。
后果是：任何持有有效 `access_token` 的人，都能用自己控制的号码收一条验证码把账号
手机号改绑走，之后用手机号登录即接管账号。

因此本次做两件事：

1. **收紧** `POST /auth/bind-phone`：只服务「从未绑定手机号」的账号；已绑定账号返回
   `409`，必须走换绑流程。
2. **新增** `PUT /auth/phone`：旧号（验证码或密码）+ 新号验证码**双证明**，
   成功后除当前设备外全部会话失效。

## `POST /api/v1/auth/sms/send`（本次扩展校验码用途）

`purpose` 取值：

| 取值 | 验证码发往 | 用途 |
|---|---|---|
| `login` | 手机号本身 | 手机号登录 |
| `bind_phone` | 待绑定手机号 | 首次绑定 |
| `change_phone_old` | **当前已绑定**的手机号 | 换绑的旧号证明 |
| `change_phone_new` | **待换绑**的新手机号 | 换绑的新号证明 |

其余字段与限流规则（60 秒间隔、每日上限）不变，见 `认证.md`。

## `PUT /api/v1/auth/phone`

**基本信息**

- 用途：把当前账号的手机号换绑为新号
- 完整 URL：`/api/v1/auth/phone?confirm=true`
- Method：`PUT`
- 是否需要登录：是
- 所需角色/权限：任意已登录且已绑定手机号的用户
- Content-Type：`application/json`；成功响应无返回体
- 成功状态码：`204 No Content`

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 默认 | 校验 | 含义 |
|---|---|---|---|---|---|---|
| `Idempotency-Key` | header | string | 是 | — | 8–128 字符 | 幂等键；同键同载荷只执行一次 |
| `confirm` | query | boolean | 是 | `false` | 必须为 `true` | 敏感操作二次确认，缺省返回 `428` |
| `new_phone` | body | string | 是 | — | `^1[3-9]\d{9}$` | 新手机号 |
| `new_code` | body | string | 是 | — | 6 位数字 | 新号验证码（`purpose=change_phone_new`） |
| `old_code` | body | string | 条件 | `null` | 6 位数字 | 旧号验证码（`purpose=change_phone_old`）；与 `password` 二选一 |
| `password` | body | string | 条件 | `null` | 1–64 字符 | 账号密码；与 `old_code` 二选一 |

`old_code` 与 `password` 至少提供一个，否则 `422`。

**请求示例**

```http
PUT /api/v1/auth/phone?confirm=true
Authorization: Bearer <access_token>
Idempotency-Key: change-phone-20261102-0001
Content-Type: application/json
```

```json
{
  "new_phone": "13900000002",
  "new_code": "222222",
  "old_code": "111111"
}
```

非法示例（缺旧号证明 → 422）：

```json
{ "new_phone": "13900000002", "new_code": "222222" }
```

**返回参数**

无返回体（`204`）。

**错误**

| HTTP | 触发条件 | 响应示例 | 前端处理 |
|---|---|---|---|
| 401 | 未登录、token 失效、账号密码错误 | `{"detail":"账号密码错误"}` | 密码错时留在页面提示；token 失效跳登录 |
| 404 | 用户不存在 | `{"detail":"用户不存在"}` | 退出登录 |
| 409 | 账号尚未绑定手机号 | `{"detail":"账号尚未绑定手机号，请使用绑定流程"}` | 改走 `POST /auth/bind-phone` |
| 409 | 新号已被其他账号绑定 | `{"detail":"该手机号已绑定其他账号"}` | 提示更换号码 |
| 422 | 新旧号相同 | `{"detail":"新手机号与当前手机号相同"}` | 提示无需换绑 |
| 422 | 缺旧号证明、号码/验证码格式非法 | pydantic 校验数组 | 按字段提示 |
| 400 | 验证码错误或已过期 | 短信服务错误响应 | 提示重新获取验证码 |
| 428 | 未带 `confirm=true` | `{"detail":"敏感操作需要二次确认：请携带 confirm=true"}` | 补 `confirm=true` 重试 |

**使用方法与业务规则**

1. **前置条件**：登录；当前账号已绑定手机号（未绑定走 bind 流程）。
2. **调用顺序**：先 `POST /auth/sms/send`（`purpose=change_phone_old`，发往旧号）→
   `POST /auth/sms/send`（`purpose=change_phone_new`，发往新号）→ `PUT /auth/phone`。
3. **幂等**：必须带 `Idempotency-Key`；同键同载荷重复提交不重复改绑。
4. **会话失效**：成功后除发起请求的当前设备外，该账号其他会话全部置为失效
   （`revoke_reason='phone_changed'`），需要重新登录。
5. **事务与并发**：新旧号均在事务内 `FOR UPDATE`，并发换绑同一号码只会成功一次。
6. **边界**：新号与他人重复 → 409；验证码过期 → 400；已绑定用户误用 bind → 409。

## 前端接入建议

- 设置页「换绑手机号」入口接本文接口；`bind-phone` 只用于「微信登录后补绑」。
- `409 / 尚未绑定` 时应自动切到绑定流程，而不是报错。
- `428` 说明缺少二次确认，属于前端 bug，不要重试同一请求。
