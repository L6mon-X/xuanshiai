# 提示词优化指南（面向项目负责人）

> 本文件不是项目规则，不进入 AGENTS.md / CLAUDE.md 的必读路径；项目规则见 PROJECT_RULES.md。

这份文档只回答一个问题：怎样把任务写成 Agent 能稳定执行、你能快速验收的提示词。规则条款不在这里展开，只引用 `PROJECT_RULES.md` 的小节号。

## 一、四条底层原则

### 1. 提示词是规格，不是建议

“优化一下”“处理好”“尽量完善”不是规格。规格要能回答：改什么、不改什么、什么算完成、失败时怎么报告。提示词的默认读者是执行者，不是猜意图的人。

### 2. 结构胜过散文

同一组约束，写成“目标 / 范围 / 规则 / 验收 / 输出”比藏在三段说明文里可靠。Agent 会逐段执行，也会逐段漏掉；结构让遗漏可见。

### 3. 示例胜过指令

一个真实的请求示例、一段期望输出、一条实际命令，胜过“格式要规范”这类形容词。示例还能顺手暴露边界：空值、失败、无权限、重复提交。

### 4. 验证必须结构化

验收要落到可执行命令、可检查文件、可对比输出和退出码。没有验证方式的“已完成”只是叙述，不是证据；对应 `PROJECT_RULES.md` 1.6。

## 二、五段式任务模板

### 2.1 身份与目标

```text
你是 <角色>，负责 <系统或模块>。
本次只解决 <一个可验收的问题>。
目标结果是 <用户可观察的结果>，不是“执行以下步骤”。
```

常见问题：把目标写成步骤清单。步骤是手段，目标才是验收对象。

### 2.2 范围与边界

```text
允许修改：<文件/目录清单>。
禁止修改：<接口契约、依赖、CI、测试、其他模块>。
如必须越界，先停止并说明原因，不要自行扩大范围。
```

对应 `PROJECT_RULES.md` 1.5。范围越具体，越不容易出现“顺手重构”。

### 2.3 约束与规则

```text
必须遵守 PROJECT_RULES.md 的 <小节号>。
优先复用 <现有模块/函数/依赖>，不新增依赖（或：新增依赖前先说明理由）。
关键约束：
- <约束 1>
- <约束 2>
- <约束 3>
```

只写真正会改变执行结果的约束；规则引用写小节号，不复制正文。对应 `PROJECT_RULES.md` 2.4、第八章。

### 2.4 验收标准

```text
验收标准（全部满足才算完成）：
1. <可执行命令或可检查结果>
2. <可执行命令或可检查结果>
3. <边界/失败场景也通过>
不满足任一条，报告未完成并说明卡在哪一条。
```

验收标准要能逐条判定“通过/不通过”。不要写“代码质量良好”“功能正常”这类无法取证的标准。

### 2.5 输出格式与证据要求

```text
输出：
1. 改动文件清单。
2. 任务标识：<issue 号 / docs/待完成事项.md 条目号 / 工单号>。
3. 每条验收标准对应的命令原文、退出码、关键输出摘录。
4. 未完成项、风险与回滚方案（如适用）。
缺少证据的“已完成”视为未完成。
```

对应 `PROJECT_RULES.md` 1.6、1.7、第五章。完整模板可以直接拼接上面五段使用。

## 三、按任务类型写提示词

| 任务类型 | 必须写清 | 常见坑 |
| --- | --- | --- |
| 编码实现 | 目标行为、输入输出、错误场景、允许修改的文件、接口/迁移要求、测试命令 | 只写“实现某功能”不写边界；允许 Agent 自行改接口；没有回归命令 |
| 代码审查 | 审查范围、审查维度（安全/契约/并发/兼容性）、严重级别、只审查不修改 | 把审查写成“看看有没有问题”；只报风格；意见没有文件行号 |
| 方案评估 | 业务约束、候选方案、比较维度、决策标准、是否允许实施；要求按 `PROJECT_RULES.md` 6.4 格式输出五维评判 | 只给一个方案让 Agent 背书；不写成本/安全/回滚；评估完直接开工 |
| 排障 | 现象、复现步骤、影响范围、已知日志、允许的修复边界、回归验证 | 同时改多个变量；没有基线；修完不跑原复现路径 |
| 重构 | 保持不变的行为、现有测试基线、分步范围、回滚方式 | 重构夹带功能变更；一次改太多；没有前后对比证据 |

## 四、反模式自查清单

提交提示词前逐项检查：

- [ ] **模糊措辞**：是否还有“优化一下”“处理干净”“尽量完善”？改成可验收的结果。
- [ ] **目标写成步骤**：是否把“先改 A 再改 B”当成了目标？补一句最终可观察结果。
- [ ] **无验收命令**：是否只写“完成后告诉我”？补命令、退出码和关键输出要求。
- [ ] **未限定可修改文件范围**：是否没说哪些能改、哪些不能改？补允许/禁止清单。
- [ ] **未说明是否允许新增依赖**：是否既没说可以，也没说禁止？明确写“不新增依赖”或“先说明理由”。
- [ ] **关键约束放在长段落中间**：是否会被背景说明淹没？移到末尾，改成短句清单。
- [ ] **一次任务塞多个不相关目标**：是否同时要求修 bug、重构、补文档、升级依赖？拆成多次任务。
- [ ] **提示词超过 3 页**：是否把背景、历史、规则全文都贴进来了？只留执行所需信息和规则小节号。

## 五、篇幅控制

- 单次任务控制在 2 页以内；超过 2 页通常说明目标不单一，或背景没有裁剪。
- 引用项目规则只写小节号，例如“遵守 `PROJECT_RULES.md` 1.6、7.2”，不要复制规则正文。
- 关键约束放在提示词末尾，利用最近阅读位置；背景材料放前面或作为附件。
- 一个任务只保留一个主目标；相关但可拆的改动写成“后续任务”，不塞进本次验收。

## 六、提交前 30 秒自检

1. 目标能否用一句话说清，验收能否逐条判定？
2. 允许修改和禁止修改是否都写全？
3. 是否明确“不新增依赖”或新增依赖的审批条件？
4. 关键约束是否在末尾、是否不超过 5 条？
5. 输出是否要求命令原文、退出码、关键输出和任务标识？

## 附录：可复用证据契约块

把下面整段放在提示词末尾，作为完成声明的硬门槛：

```text
任何“已完成”“已修复”“已通过”“已验证”的声称，必须附随：所执行命令的原文、完整 stdout/stderr、退出码。缺少任一要素的完成声明，视为未完成。命令失败则报告失败；无法执行则报告无法执行；不得以“已处理”“已修复”等无证据措辞替代。不适用命令验证的纯文档或纯审查任务，须给出所依据的文件路径与行号作为证据。
```
