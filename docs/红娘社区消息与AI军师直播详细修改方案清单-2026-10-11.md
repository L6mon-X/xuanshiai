## 二、口径与优先级

### 2.1 优先级定义

| 级别 | 判定标准 | 处理时限 |
| --- | --- | --- |
| **P0** | 代码缺陷、安全边界漏洞、功能实际不可用 | 立即，本批次内必须关闭 |
| **P1** | 产品闭环关键环节缺失，影响业务可运营性 | 本迭代内 |
| **P2** | 运营完善、体验优化、文档一致性 | 排期靠后 |

### 2.2 工时口径

- 单位：**人日**（1 人日 = 8 小时），含编码 + 自测 + 文档同步，不含 Code Review 等待与真实环境演练。
- 估算基准为熟悉本项目的 1 名后端工程师；多人并行时按依赖关系折算。
- 标注 `≤0.5` 的条目通常可在半日内连同类回归一起完成。

### 2.3 完成定义

一条任务标记为已完成，必须同时满足：

1. 代码已提交，且**路由可被真实调用**（仅存在服务函数不算）；
2. 有对应的自动化测试（单元或集成），或说明为何无法自动化；
3. 相关 `docs/api/*.md` 已同步；
4. 属于权限/数据范围类的，附**真实多组织账号**的越权验证记录（可延后到批次 4 统一做，但必须留 TODO 标记）。

### D-9 敏感操作统一幂等覆盖不全【严重度：中】

**现状**：`require_sensitive_operation`（`app/api/dependencies.py:20-42`）已对 5 个端点生效（重置密码、订单退款、提现审核、结束资源分配、移除门店成员），但**资源分配、CRM 会员改派、批量改状态**三类高影响写操作仍未接入：
- 分配资源：`matchmaker_admin.py:175-177` → `organization.py:112-133`。
- CRM 改派：`matchmaker_crm_admin.py:359-390`。
- 批量改状态：`matchmaker_crm_admin.py:209-223`。

**修改方案**
1. 为上述 3 组端点挂 `require_sensitive_operation`，operation 命名遵循 `模块.对象.动作` 规范（如 `matchmaker.crm.reassign`）。
2. 复用现有事务编排（`sensitive_operations.begin/finish/abort`），**不新增实现**。
3. 补测试：同 `Idempotency-Key` 重复提交只生效一次；缺 `confirm=true` 返回 428。

**验收标准**：3 组端点缺键返回 422、缺二次确认返回 428；重复提交不产生重复资源变更；均有审计。

### D-10 旧版红娘分支/资源分配路由无数据范围【严重度：高，越权】

**现状（10-04 D-4 的未覆盖残留）**：新版 `/stores` 体系已下沉作用域，但**旧版路由仍与新版并存且无范围过滤**：
- `GET /admin/matchmaker/branches`、`GET /admin/matchmaker/branches/{id}`：`matchmaker_admin.py:155-167` → `organization.list_stores/get_store` 无 admin 作用域。
- `GET /admin/matchmaker/assignments`：`matchmaker_admin.py:180-194`，`conditions = ["1=1"]`（`:182`）**返回全平台资源分配**。
- `POST /admin/matchmaker/assignments`：`matchmaker_admin.py:175-177`、`POST .../branches/{id}/members`：`:170-172` 无作用域校验。
- 红娘申请审核列表/详情：`identity.py:80-104` 无作用域。

**修改方案**
1. 二选一的明确决策（需产品/架构确认）：
   - **方案 A（推荐）**：旧版路由标注 `deprecated` 并从 OpenAPI 隐藏，内部重定向到新版 `/stores` 体系，前端切换后删除；
   - **方案 B**：保留旧版，但全部套用 `CurrentMatchmakerAdmin.scope_clause`。
2. 无论 A/B，`GET /assignments` 的 `1=1` 必须立即消除（当前**任何门店管理员都能看到全平台分配**）。
3. 红娘申请审核列表/详情补作用域。
4. 补越权回归：门店 A 账号访问门店 B 的分支/分配/申请 → 0 条或 403。

**验收标准**：旧版路由在「A 组织账号访问 B 组织数据」时返回 0 条或 403；`GET /assignments` 不再出现 `1=1` 无过滤查询。

## 六、验收标准（按类别）

### 6.1 功能类

- 每条新增/修复路由均能在 OpenAPI 文档中看到，且文档描述与实际行为一致。
- 所有「涉及金额」的动作（支付、开通、退款、提现、奖励）满足：幂等键可控、重复请求不重复扣款/发放、失败有明确状态与审计。

### 6.2 安全类

- 权限：**不存在任何走后台鉴权却不做权限校验的路由**（由 `test_admin_permission_coverage.py` 持续保证）。
- 数据范围：`ALL / SELF / STORE / ORGANIZATION` 四档均有实现，且**无绑定组织时返回 0 条**（fail-closed）；旧版路由不再出现 `1=1` 无过滤查询。
- 越权：附真实多组织账号的验证记录（A 组织账号访问 B 组织数据 → 0 条或 403）。

### 6.3 可靠性类

- 实时通道（直播 WS、聊天 WS）：Redis 不可用时 fail-closed 且给出明确关闭码；断线重连可补发。
- 异步投递（通知、直播事件、Outbox）：有重试、有死信、有崩溃恢复。

### 6.4 文档类

- `docs/api/*.md` 中出现的路径与 OpenAPI 逐条对齐（D-7 的检查方式可复用为常规核对手段）。
