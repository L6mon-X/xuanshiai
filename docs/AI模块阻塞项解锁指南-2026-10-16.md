## 1. FIX-01（改密接口权限边界）——决策点，非阻塞

### 根本原因

`get_current_matchmaker_admin` 是 **fail-closed** 依赖，准入需要三道闸**命中至少一道**：

1. `_matchmaker_admin_permission(request)`：按 URL 关键词映射权限码；
2. `_is_permission_exempt(path)`：认证类端点后缀白名单；
3. 路由函数上的 `@declare_permission(...)`。

`POST /api/v1/admin/matchmaker/auth/change-password`（`app/api/routes/matchmaker_admin.py:85`）**三闸全部未命中**，于是对**任何调用者**（含合法后台账号）恒返回 `403`。

- 引入提交 `d8cbcd1`（2026-10-13），**晚于**覆盖测试 `bafa20f`（2026-10-04）⇒ 是真实回归。
- 定性：**功能失效，不是越权**。fail-closed 拒绝而非静默放行；密码逻辑本身正确（`FOR UPDATE`、bcrypt 重哈希、审计落库俱全）。
- 长期未被发现的原因：唯一涉及它的 `tests/test_admin_password_change_contract.py` **只断言路由已注册，不覆盖运行时**。

### 解决思路与完整步骤（方案 A，已在工作区实施）

```python
# app/api/dependencies.py
PERMISSION_EXEMPT_SUFFIXES: tuple[str, ...] = (
    "/admin/matchmaker/auth/me",
    "/admin/matchmaker/auth/logout",
    "/admin/matchmaker/auth/change-password",   # 本次新增
)
```

边界收紧依据：路由体内句柄锁死 `current.account.id`，**只能改自己的密码**，不引入横向越权面。配套行为级测试 5 例（匿名 401 / 非后台令牌 401 / 成功 204 且旧密码立即失效 / 旧密码错 400 / 新旧相同 400）。已在 `docs/api/后台账号修改密码.md` 补「变更记录」。

## 4. FIX-11（记忆全生命周期真实库补验）——**本次解锁（记忆域），其余待 Redis/Provider**

### 根本原因

### 解决思路与完整步骤（已完成）

### 本次由此暴露的真实缺陷（**2 处，均为测试自身缺陷，已修复**）

**缺陷 A — 陈旧前置断言**：`tests/integration/ai/test_ai_memory_purge_grant_fence_real_db.py`

- 该测试（`bc1ebdb`，2026-10-08）断言「同秒撤回+重新授权 ⇒ 快照相同」，理由是 `granted_at` 仅秒级精度。
- 但 `ce72b9e`（2026-10-10，「记忆授权修正」）已把快照改为绑定**持久 `grant_id`**（`app/services/ai/memory/projections.py:derive_consent_snapshot_id` 的 `generation` 字段）⇒ 每次授权都是新代，快照**必然不同**。
- 因此该断言自 10-10 起恒红，**但从未有环境跑过它**（CI 无真实库、本机无 Docker、文档命令一律 `--ignore=tests/integration`）。
- 判定：**陈旧测试，非产品缺陷**。新设计（绑定 `grant_id`）比旧的「靠时间精度区分代际」**严格更强**。
- 修复：断言改为 `new_snapshot != old_snapshot`，并注明绑定 `grant_id` 后**无条件**区分代际、清理侧按「不属于当前快照」判定在同秒与跨秒两种情形下都成立。（该测试自身的守卫文案早已预言此情形：「若无条件相等被打破，说明授权表新增了可区分代际的列……需重新评估」。）

**缺陷 B — 引用不存在的列**：`tests/integration/ai/test_ai_memory_real_db.py:290`

- 查询写成 `SELECT source_kind, status, confidence FROM ai_memory_observation WHERE owner_user_id = :owner ORDER BY id`。
- 但 `ai_memory_observation` 的主键是 **`observation_id`（varchar）**，**从无 `id` 列**（`app/db/ai_schema.py:736` 与 `migrations/ai/20260905_01_memory_kernel_core_up.sql:46` 一致；迁移亦未补该列）。
- 报错：`(1054, "Unknown column 'id' in 'order clause'")`。该断言的后续逻辑用 `by_confidence` 字典取值、**并不依赖排序**，故 `ORDER BY` 实为冗余。
- 修复：`ORDER BY id` → `ORDER BY observation_id`。
